# ESP32-S3 智能语音办公闹钟技术实现说明

## 1. 文档定位

本文档用于说明当前仓库中固件代码的实际技术实现方式。

本文档只描述已经进入当前代码主线的实现，不展开历史方案，也不冻结未来规划。

---

## 2. 软件平台

当前项目的软件平台为：

- `ESP-IDF 6.0.1`
- `FreeRTOS`
- `LVGL`

主控芯片为 `ESP32-S3`。系统通过 `ESP-IDF` 提供的驱动和组件完成：

- 显示控制
- 按键输入
- 传感器采集
- 人体存在检测
- 网络连接
- 时间同步
- 音频播放
- 本地配置与缓存持久化

---

## 3. 当前工程结构

### 3.1 启动与模块编排

工程入口位于：

- `src/main.c`
- `src/app_boot.c`
- `src/app_module.c`

其中：

- `main.c` 负责调用系统启动入口
- `app_boot.c` 负责启动和关闭流程
- `app_module.c` 维护模块注册表，并按顺序执行 `init/start/stop`

当前模块注册顺序包括：

- `fault_state`
- `persistence_broker`
- `app_bus`
- `settings_model`
- `timebase_service`
- `display_service`
- `backlight_service`
- `input_service`
- `ui_model`
- `environment_service`
- `presence_service`
- `audio_service`
- `net_service`
- `sync_service`
- `reminder_service`
- `lifecycle_service`

这意味着当前系统已经采用“模块 owner 明确、统一编排启动”的实现方式，而不是把全部逻辑集中在单个主循环中。

### 3.2 功能模块划分

按当前目录划分，主要模块如下：

- `src/modules/interaction/`
  - 负责显示、背光、按键和界面模型
- `src/modules/sensing/`
  - 负责环境采样和人体存在检测
- `src/modules/connectivity/`
  - 负责 Wi-Fi、IP 状态、SNTP 时间同步，以及通用 HTTP 请求能力
- `src/modules/sync/`
  - 负责 Web 配置拉取、Todo 同步、设备状态上报、设备事件上报和本地配置写回
- `src/modules/audio/`
  - 负责提示音与语音播放
- `src/modules/config/`
  - 负责参数模型与持久化
- `src/modules/core/`
  - 负责故障状态、生命周期、中心事件总线和时间基线辅助模块
- `src/modules/reminder/`
  - 负责提醒触发逻辑

### 3.3 模块边界与中心事件总线

当前固件把网络连接和业务同步拆分为两个模块：

- `net_service` 只维护 Wi-Fi/IP/SNTP 状态，并提供 `net_service_http_request()` 作为低层 HTTP 能力。
- `sync_service` 拥有 Web 侧业务协议、Todo 缓存、配置版本、状态上报、事件上报、写回重试和退避策略。

业务模块之间不直接调用彼此的 Web 同步接口。需要跨模块传播的业务动作通过 `app_bus` 发布，例如：

- UI 发布 Todo 完成/删除请求
- UI 或提醒模块发布闹钟/语音配置已变更
- 提醒模块发布 `alarm_triggered`、`env_alert_triggered`、`rest_reminder_triggered` 等设备事件
- 输入模块发布按键事件，UI 订阅后进入自己的按键队列
- UI 和提醒模块发布语音播放请求，音频模块订阅后进入自己的播放队列
- UI 或 Web 更新运行设置后发布设置变更，环境模块订阅后自行调整采样周期
- `sync_service` 订阅这些事件，并异步转成对应的 Web 请求

这样 `ui_model`、`reminder_service`、`input_service` 等业务/交互模块只表达本地动作，具体 owner 模块通过注册回调消费事件；`sync_service` 负责同步可靠性，`net_service` 只负责网络能力。

`sync_service` 对网络失败做集中处理：

- 配置拉取和状态上报使用指数退避，避免离线时持续打满请求。
- 设备事件上报失败后进入延迟重试队列。
- Todo 完成/删除、闹钟写回、语音设置写回失败后进入延迟重试队列。
- 状态型写回请求会用最新配置覆盖旧的待重试配置，避免离线期间重放过期设置。

## 4. 显示与交互实现

### 4.1 显示链路

显示由 `display_service` 统一负责，底层使用：

- `SPI`
- `esp_lcd`
- `LVGL`

当前屏幕参数：

- 分辨率：`240x320`
- 驱动芯片：`ST7789`

`display_service` 的职责主要是：

- 初始化显示硬件
- 建立 `LVGL` 运行环境
- 提供界面渲染所需的底层屏幕与任务支持

### 4.2 当前真实 UI 主线

当前实际页面主线由 `ui_model.c` 驱动，不再是早期草图中的 `HOME / SETTINGS / NETWORK / POWER` 结构。

当前主页面为：

- `HOME`
- `ALARM`
- `TODO`
- `ENV`
- `WIFI`
- `LOW_CLOCK`

此外，还有若干设置或编辑视图，例如：

- `HOME_SETTINGS`
- `ALARM_SETTINGS`
- `ALARM_ITEM`
- `TODO_SETTINGS`
- `TODO_ITEM`
- `TODO_DELETE_CONFIRM`
- `ENV_SETTINGS`
- `LOW_SETTINGS`

界面按键使用 4 个独立物理键完成。按键不是固定绑定单一功能，而是根据当前页面和当前视图状态切换语义。

当前界面逻辑主要集中在 `ui_model.c` 中实现，负责：

- 页面切换
- 页面渲染
- 设置项编辑
- 闹钟管理
- Todo 项查看、同步、完成与删除操作

## 5. 环境感知实现

### 5.1 温湿度与光照

环境采样由 `environment_service` 负责。

当前接入硬件为：

- 温湿度：`DHT11`
- 光照：`BH1750`

实现方式：

- `DHT11` 通过本地读取逻辑结合 `dht` 组件完成采样
- `BH1750` 通过 `I2C` 读取照度数据

服务会维护最近一次环境快照，并向其他模块提供：

- 温度
- 湿度
- 光照
- 数据有效位

### 5.2 环境参数与阈值

当前系统中的环境阈值来自 `settings_model`，可在运行时调整，主要包括：

- 温度上下限
- 湿度上下限
- 光照上下限
- 环境采样周期
- 环境提示开关
- 环境语音开关

界面显示与提醒逻辑都基于这些阈值工作。

---

## 6. 人体存在检测实现

人体存在检测由 `presence_service` 负责。

当前硬件为：

- `LD2410C`

当前实现同时使用：

- `UART` 数据流
- `OUT` 引脚状态

服务内部会把两路信息融合，输出：

- 当前是否检测到人
- 雷达是否健康
- 当前是否使用 `OUT` 回退判断

该结果会被用于：

- `LOW_CLOCK` 低干扰时钟页的进入与退出
- 欢迎提示触发
- 休息提醒累计

## 7. 音频实现

### 7.1 硬件链路

当前音频输出链路为：

- `ESP32-S3`
- `I2S`
- `MAX98357A`
- 扬声器

### 7.2 播放方式

音频由 `audio_service` 统一负责。

当前提示音资源以 `WAV` 文件形式嵌入固件，资源位于：

- `assets/audio/`

构建时通过 `src/CMakeLists.txt` 嵌入。

运行时流程为：

1. 其他模块通过 `app_bus` 发布语音播放请求
2. `audio_service` 根据事件找到对应 `WAV`
3. 从 `WAV` 中提取 `PCM` 数据
4. 通过 `I2S` 写入 `MAX98357A`
5. 扬声器发声

当前已接入的主要音频事件包括：

- 欢迎提示
- 联网成功提示
- Todo 同步提示
- 环境异常提示
- 休息提醒
- 闹钟提醒

音量通过对 `PCM` 样本做比例缩放实现。

## 8. 网络与时间同步实现

### 8.1 Wi-Fi

网络由 `net_service` 负责。

当前实现采用固定热点模式：

- 启动后自动连接配置中的固定 Wi-Fi
- 断线后按周期自动重试
- 也支持手动触发一次立即连接

网络状态对外提供：

- Wi-Fi 是否启动
- 是否已连接
- 是否已拿到 IP
- 当前 SSID
- 当前 IP 地址
- 时间是否已同步

### 8.2 时间同步

当前时间同步方式为：

- `SNTP`

实现流程为：

1. Wi-Fi 连接并获取 IP 后立即启动一次 `SNTP`
2. 后续通过定时器周期性再次同步
3. 本地时区通过 `TZ` 和 `tzset()` 配置

时间同步状态会影响：

- 界面时间显示
- 闹钟触发
- 与绝对时间相关的提醒逻辑

### 8.3 Todo 同步

Todo 同步由 `sync_service` 负责。

当前实现方式为：

- 通过 `net_service_http_request()` 使用 `HTTP GET` 从 Web 端拉取设备配置
- 从设备配置中解析 active Todo、闹钟配置、语音配置和配置版本
- 成功后更新本地 Todo 缓存和运行配置
- 失败时保留旧缓存，记录错误信息，并进入指数退避

此外，当前还支持：

- UI 通过 `app_bus` 手动触发一次同步
- UI 通过 `app_bus` 请求 Todo 完成
- UI 通过 `app_bus` 请求 Todo 删除
- 把 Todo 缓存写入本地 `NVS`

其中，设备端对 Todo 的完成 / 删除不会由 UI 直接访问网络；`sync_service` 订阅对应事件后发起 Web 请求，成功后再更新本地缓存状态，失败则进入延迟重试队列。

因此，当前 Todo 链路已经不是单纯“只读展示”，而是具备基础双向操作能力。

## 9. 提醒逻辑实现

提醒逻辑由 `reminder_service` 负责。

当前已接入的提醒能力包括：

- 闹钟触发提醒
- 整点提示音
- 环境异常提示
- 休息提醒
- 新 Todo 项检测提示

其中：

- 闹钟提醒依赖当前时间与本地闹钟配置匹配
- 休息提醒依赖连续在位时间累计，当前阈值为连续在位 3 小时且单次会话只触发一次
- 环境提醒依赖环境阈值判断
- Todo 提示依赖同步后发现新的未完成事项，并播放独立的同步提示音

这部分逻辑说明项目已经从“只显示信息”发展到“根据状态主动提醒”。

## 10. 配置与持久化实现

配置由 `settings_model` 与 `persistence_broker` 共同支持。

当前配置内容包括：

- 首页显示模式
- 12/24 小时制
- 整点提示开关
- 闹钟语音开关
- Todo 语音开关
- 环境语音和提醒开关
- Todo 自动刷新周期
- 环境采样周期
- 环境阈值
- `LOW_CLOCK` 进入和退出阈值
- 闹钟列表

这些设置会写入 `NVS`，设备重启后可以恢复。

## 11. 当前实现特点

从当前代码实现看，本项目的主要技术特点包括：

- 基于 `ESP-IDF` 的模块化固件结构
- 使用 `LVGL` 构建小屏图形界面
- 使用 `DHT11`、`BH1750`、`LD2410C` 形成环境与在位感知能力
- 使用 `I2S + MAX98357A` 实现语音与提示音播放
- 使用 `Wi-Fi + SNTP + HTTP` 完成联网校时与 Todo 同步
- 使用 `NVS` 保存本地设置和 Todo 缓存

这些能力共同构成了当前智能语音办公闹钟原型的技术基础。

## 12. 当前边界说明

以下内容在当前代码中仍属于未完全成熟或后续可继续优化部分：

- `DHT11` 仍然存在一定稳定性问题
- Todo JSON 解析仍采用轻量字符串解析，而非正式 JSON 解析器
- 网络访问目标当前仍依赖固定地址配置
- `LOW_CLOCK` 和欢迎提示等逻辑已经实现，但交互与体验仍可继续打磨
- 提醒能力已经存在，但完整业务策略仍可继续细化

因此，当前项目更适合定位为：

- 已完成主链路打通的综合实践原型

而不是：

- 已经完全收敛的量产型系统

补充：

- 后续 Web 控制中心与三通道同步扩展设计，见 `docs/plans/2026-06-09-web-device-control-center-design.md`
